## Вопрос 1. Части приложения

<a id="З3-С03"></a>

### Слайд 6. Части приложения

Рассмотрим действие через обязанности частей приложения. Браузер передаёт ввод, сервер проверяет основания операции, а база поддерживает согласованное сохранение.

<a id="З3-С04"></a>

### Слайд 7. Ответственность сервера

Браузерная часть управляет представлением и взаимодействием. Она помогает Анне заполнить форму и передаёт обращение в согласованном формате. Затем читает результат и выбирает соответствующее состояние интерфейса. Это не означает право назначить student_id или итоговый статус. Клиентские данные могут быть изменены, а локальные сведения о проекте — устареть. Поэтому сервер не считает внешний вид страницы доказательством допустимости операции.

Такое разделение полезно и при разработке. Изменение расположения поля не должно менять правило допустимой длины. Замена интерфейса не должна открывать дополнительные права. Серверный договор позволяет нескольким представлениям обращаться к одной логике. В нашем примере реализуется только согласованный веб-путь, но принцип объясняет, почему правила не прячут исключительно в код кнопки. Дальше посмотрим на сторону, которая принимает окончательное решение.

Сервер принимает запрос и применяет правила независимо от состояния страницы. Он определяет пользователя по сеансу, проверяет структуру данных и право выполнить действие. Для создания заявки нужен студент, открытый существующий проект, допустимая мотивация и отсутствие предыдущей пары. Затем сервер организует сохранение. Только после подтверждения записи можно формировать успешный результат. Такой порядок исключает обещание действия, которое ещё не завершилось.

На схеме показаны логические шаги, а не обязательное число функций в программе. Реализация может распределить их между несколькими частями. Существенно, чтобы проверки не исчезли и чтобы ошибка ограничения данных превратилась в понятный договорённый ответ. Если два обращения пришли почти одновременно, простое предварительное чтение ещё не гарантирует отсутствие повтора. Этот случай позже разберём на временной последовательности.

<a id="З3-С05"></a>

### Слайд 8. Роль базы в обмене

Проследим связь результата с сохранёнными данными. Запрос браузера запускает обработку, но общей заявки в этот момент ещё может не быть. Сервер проверяет условия, обращается к базе и только после подтверждённого сохранения готовит ответ с номером 104.

Обратные связи схемы нужны не для симметрии рисунка. Они показывают, какое свидетельство получает следующая часть: сервер узнаёт результат работы с данными, браузер получает подтверждение от сервера. Если оборвать последнюю передачу, состояние базы уже может измениться. Поэтому отсутствие подтверждения в браузере не отменяет выполненную запись и требует отдельного уточнения результата.

## Вопрос 2. HTTP и JSON

<a id="З3-С06"></a>

### Слайд 11. HTTP и JSON

Разберём, что именно передаётся по сети: адрес, метод, заголовки, тело и результат. Корректное сообщение ещё не означает, что предметная операция разрешена.

<a id="З3-С07"></a>

### Слайд 12. Адрес запроса

Эйч-ти-ти-пи, HTTP, расшифровывается как Hypertext Transfer Protocol. Это протокол, то есть согласованные правила обмена. Клиент отправляет запрос, сервер возвращает ответ. Запрос указывает операцию и адрес, а при необходимости содержит данные. Ответ содержит код результата и может передавать представление ресурса. Наш фрагмент сокращён, чтобы показать смысл основных частей. Он не является полным сетевым пакетом и не требует ручного ввода.

Метод GET в этом примере запрашивает каталог. Адрес /api/projects обозначает согласованный путь нашей системы. Заголовок Accept показывает предпочтительный формат ответа. HTTP не определяет, как именно устроена таблица проектов или какой интерфейс увидит Анна. Эти решения принадлежат приложению. Протокол даёт общий язык обмена, на котором можно выразить наш проектный договор.

Адрес запроса состоит из частей. Схема задаёт способ обращения, имя узла помогает найти нужный сервис, путь указывает ресурс внутри приложения. В нашем примере projects.example.test является условным доменом для пояснения. К нему не нужно переходить. В рабочих примерах далее будем показывать только путь, потому что обсуждаем договор приложения. Число семнадцать в пути выбирает конкретный проект из общего набора.

Адрес сам по себе не выражает все полномочия. Человек может узнать или изменить число в строке, поэтому сервер проверяет право при каждом защищённом действии. Мы также не выводим из одного технического пути обязательный вид страницы. Карточка проекта может использовать сведения этого ресурса и показывать их понятным образом.

<a id="З3-С08"></a>

### Слайд 13. Метод запроса

Метод — часть запроса, которая задаёт характер действия. GET используем для получения сведений. POST в нашем договоре создаёт заявку. PATCH передаёт частичное изменение, в данном случае решение по статусу. Эти значения не выводятся только из названия кнопки. Они должны быть согласованы между клиентом и сервером. Если действие меняет данные, нельзя проектировать его как обычное чтение только ради удобства ссылки.

При этом протокол не превращает любой POST автоматически в создание именно заявки. Конкретную операцию определяет договор приложения вместе с путём и форматом. Для PATCH также необходимо описать, какие изменения разрешены. В нашем примере не допускается произвольная правка студента, проекта и мотивации через маршрут решения. Передаётся только итоговый статус из согласованного набора. Остальные условия проверяются сервером.

Метод и адрес задают операцию; заголовки помогают интерпретировать передаваемое содержимое.

<a id="З3-С09"></a>

### Слайд 14. Заголовки

Заголовки передают сведения о сообщении и условиях обмена. Content-Type сообщает, как понимать тело запроса или ответа. Значение application/json обозначает формат JSON, который скоро разберём. Accept выражает предпочтение клиента по представлению результата. Эти заголовки имеют разное назначение, хотя в примере значения одинаковы. Заголовок не является произвольной строкой для декоративного комментария; его смысл задан правилами обмена.

В упрощённых фрагментах механизм сеанса не показан. Это не означает отсутствие входа. Мы заранее считаем его действующим и отдельно объясняем, что сервер получает пользователя из доверенного контекста. Пропущенные технические детали отмечаются, чтобы ведущий не принимал короткую запись за полный набор необходимых сведений. На экране достаточно двух строк для понимания формата передаваемых данных и ожидаемого результата.

<a id="З3-С10"></a>

### Слайд 15. Тело запроса

Тело содержит данные для конкретного действия. При создании заявки Анна передаёт выбранный проект и мотивацию. Поля student_id нет: пользователь определяется сервером. Поля status тоже нет: начальное состояние задаётся по правилу создания. Такой договор уменьшает неоднозначность и не даёт клиенту выбирать полномочия через обычное содержимое формы. Число семнадцать совпадает с карточкой, а мотивация — с подготовленным текстом.

Если в запрос неожиданно добавили status со значением accepted, обработка не должна принять его как разрешение на одобрение. Для учебного договора неизвестные поля отклоняются как неподдерживаемое содержимое. Решение преподавателя выполняется отдельной операцией и с отдельной проверкой права. Это разделение помогает понять, почему модель хранения может содержать больше полей, чем клиент передаёт при создании объекта.

Клиент передал входные данные; теперь разберём, что сервер вправе сообщить после обработки.

<a id="З3-С11"></a>

### Слайд 16. Ответ сервера

В ответе сервер сообщает результат. Код двести один, Created, означает создание ресурса. Заголовок Location указывает его идентификатор в адресном виде. В теле кратко показаны номер заявки, проект, студент и начальный статус. Это сокращённое представление: мотивация и время не исчезли из сохранённых данных. Мы опустили их ради читаемости. Успех отправляется после подтверждения сохранения, а не после одного получения текста запроса.

Указанный Location не добавляет в учебный договор новую обязательную операцию чтения по этому адресу. Согласованный способ Анны проверить свои обращения — GET /api/my/applications. Адрес созданного ресурса и перечень поддержанных операций являются связанными, но разными частями договора. Такое уточнение сохраняет исходный набор маршрутов и не заставляет ведущего придумывать неописанный запрос.

<a id="З3-С12"></a>

### Слайд 17. Формат JSON

Джей-сон, JSON, расшифровывается как JavaScript Object Notation. Это текстовый формат представления структурированных данных. Имя поля записывается строкой в двойных кавычках, затем идёт двоеточие и значение. Число и логический признак отличаются от строки. Фигурные скобки группируют поля объекта, квадратные могут обозначать массив. Формат не ограничивает обмен одним языком программирования, несмотря на историю названия.

В примерах важно сохранять точные имена. project_id и projectId были бы разными именами, если договор не описал преобразование. Мы используем единый вариант с подчёркиванием. JSON задаёт форму записи, но не проверяет, существует ли проект и допустима ли мотивация. Корректно разобранный текст ещё должен пройти правила приложения. Поэтому следующий шаг — различить группы результатов и конкретные причины отказа.

<a id="З3-С13"></a>

### Слайд 18. Группы результатов

Код сообщает общий класс результата, а тело уточняет причину. 200 и 201 различают успешное выполнение и создание; 401 указывает на неподтверждённый вход, 403 — на запрет действия. Если нужный ресурс не найден, в договоре предусмотрен 404.

Код 409 связан с конфликтом текущего состояния, например повтором пары, а 422 — с недопустимым содержимым понятного запроса. Серверный сбой относится к 5xx. Отсутствие ответа не является ещё одним известным кодом: браузер не получил достоверного результата и не должен самостоятельно выбирать между «сохранено» и «не сохранено».

## Вопрос 3. Договор API

<a id="З3-С14"></a>

### Слайд 21. Договор API

Из элементов сообщения соберём договор конкретных операций. Для каждого обращения важны не только путь и поля, но также пользователь, условия и виды результата.

<a id="З3-С15"></a>

### Слайд 22. Получение каталога

Эй-пи-ай, API, означает application programming interface, программный интерфейс приложения. В нашем разборе это договор обмена между браузером и сервером. Он описывает операции, форматы, условия доступа и результаты. Перечня адресов недостаточно. Клиенту нужно знать, что передавать и как понять ответ. Серверу — какие правила применить. Договор позволяет создавать части приложения согласованно, даже если их реализуют отдельно.

Мы фиксируем шесть операций из исходного плана. Их имена не меняются на следующих слайдах. Если понадобится расширение, оно будет объявлено отдельно. Это особенно важно для «моих заявок»: сервер получает текущего пользователя из сеанса, а не требует student_id в свободной строке. На следующих слайдах пройдём каждую операцию и покажем её связь с экраном и моделью данных.

Каталог запрашивает набор проектов. Метод GET не создаёт заявку и не меняет её статус. В сокращённом ответе показан один учебный проект. Массив может содержать несколько элементов или быть пустым. Каждая карточка строится из собственных данных. Показанный номер связывает выбор с последующим запросом конкретного проекта. Мы не добавляем в ответ мотивации студентов, потому что они относятся к другому ресурсу и не нужны для выбора темы.

Пустой успешный массив отличается от ошибки загрузки. При пустом каталоге интерфейс сообщает отсутствие доступных записей. При неудачном обмене он не должен утверждать, что проектов нет. Такое различие мы уже видели в состояниях интерфейса. Теперь у него появился технический источник: полученный результат и его содержимое. Сокращение ответа отмечено, чтобы модель проекта сохраняла поле description, хотя здесь оно опущено.

<a id="З3-С16"></a>

### Слайд 23. Получение проекта

Запрос конкретного проекта содержит идентификатор в пути. Ответ даёт сведения для карточки: название, описание, ответственного и доступность набора. Номер должен совпадать с тем, который Анна выбрала в каталоге. Если проект не найден, нельзя подставлять случайную карточку или показывать форму без контекста. Для учебного договора отсутствие ресурса обозначаем 404. Это отдельная ситуация от закрытого набора, при котором проект существует, но не принимает новые заявки.

Полученный is_open описывает состояние на момент чтения. До подачи оно может измениться. Поэтому сервер снова проверит проект при POST. Карточка помогает человеку принять решение, но её копия не даёт бессрочного разрешения на создание. Такая связь чтения и действия показывает, почему договор операции включает текущие условия, а не только поля.

<a id="З3-С17"></a>

### Слайд 24. Создание заявки

Эта операция создаёт новую заявку при выполненных условиях. Тело содержит project_id и motivation. Сервер определит Анну как пользователя двенадцать и назначит pending. Именно поэтому клиент не выбирает status и не присылает student_id как источник полномочия. Проект семнадцать должен существовать и быть открыт. До обработки у Анны не должно быть заявки на эту же тему. Все эти условия относятся к одному действию, хотя проверяются на разных уровнях.

Успешный ответ получит 201 и номер сто четыре. Для повтора договор предусматривает 409 с кодом APPLICATION_EXISTS. При слишком короткой мотивации будет 422. Этот набор позволяет интерфейсу выбрать конкретное состояние. Мы не отправляем одновременно два показанных успешных запроса для одного студента и проекта: последующие примеры используют разные исходные условия или обозначены как повторная попытка.

<a id="З3-С18"></a>

### Слайд 25. Получение своих заявок

Слово my в маршруте означает текущего установленного пользователя. Анна не должна передавать номер другого студента, чтобы выбрать чужие обращения. Сервер определяет её по сеансу и ограничивает выборку. В ответе показана созданная заявка сто четыре. Полный интерфейс может дополнительно получить название проекта и дату из согласованного представления. Здесь они опущены ради основной связи между пользователем и строкой.

После неопределённого результата подачи этот запрос помогает узнать, существует ли обращение. Если запись видна, интерфейс показывает её вместо новой попытки создания. Если запрос чтения тоже не получил ответ, неопределённость сохраняется. Нельзя считать пустым список, который не удалось загрузить. Такой подход связывает пользовательское восстановление с обычной операцией чтения, не вводя неописанный дополнительный маршрут для проверки.

У преподавателя другой способ отбора: нужны обращения его проекта, а не все заявки системы.

<a id="З3-С19"></a>

### Слайд 26. Получение заявок проекта

Ирина получает обращения к проекту семнадцать. Перед выдачей сервер проверяет её роль и принадлежность проекта. Одного знания адреса недостаточно. Номер проекта доступен в каталоге, поэтому сам путь нельзя считать секретом. Условие teacher_id равно текущему пользователю связывает операцию с матрицей прав. Анна не получает этот список через обычный студенческий доступ, хотя её собственная заявка присутствует среди строк.

Ответ может быть пустым, если проект существует, принадлежит Ирине и обращений ещё нет. Это нормальный результат, отличный от запрета доступа. В учебном договоре при недостаточных полномочиях возвращается 403. Интерфейс должен сообщить отказ, а не показать пустой список как будто заявок нет. Такая точность помогает и пользователю, и сопровождению отличать разные причины отсутствия содержимого.

Чтение доступных обращений ещё не разрешает любое изменение их состояния.

<a id="З3-С20"></a>

### Слайд 27. Решение по заявке

Четыре карточки показывают, почему право исполнителя и состояние записи проверяются раздельно. Из сеанса устанавливаем Ирину, по заявке находим проект и сопоставляем его teacher_id с пользователем. Только после этого обсуждаем изменение состояния.

В запросе обновления $1 — номер заявки, $2 — новое решение. Условие status='pending' относится к самой записи, которую изменяет UPDATE. Это существенно: если просто прочитать pending заранее, другой обработчик может успеть принять решение до нашей записи. Условное изменение не должно безоговорочно перезаписывать уже сохранённый итог.

В первом сценарии изменилась одна строка; после успешного COMMIT можно вернуть accepted. Во втором заявка уже accepted, поэтому условие не совпало и строк не изменено. Сам по себе ноль строк не называет единственную причину: нужно учитывать существование записи, проверенные права и актуальное состояние. В данном сценарии состояние известно, поэтому возвращаем согласованный конфликт, сохраняя accepted.

<a id="З3-С21"></a>

### Слайд 28. Единый формат ошибок

В договоре ошибки имеют единый вид. Поле code помогает программе различить причину без анализа свободной фразы. Поле message даёт человеку понятное объяснение. Текст можно редакционно уточнить, сохранив машинное обозначение. Для повтора используем APPLICATION_EXISTS. Закрытый проект получит PROJECT_CLOSED, недопустимый итоговый переход — INVALID_TRANSITION. Длина мотивации относится к ответу 422 и коду MOTIVATION_LENGTH. Это наши договорённости, а не универсальные имена стандарта HTTP.

Согласованность формата уменьшает число особых случаев в интерфейсе. Однако чувствительные внутренние подробности не нужно превращать в пользовательское сообщение. Номер таблицы или текст неожиданной ошибки базы не объясняет Анне дальнейшее действие. Сервер сохраняет технические сведения для разбора, а клиент получает предусмотренную причину. Теперь перейдём от внешнего договора к шагам внутренней обработки.

## Вопрос 4. Обработка на сервере

<a id="З3-С22"></a>

### Слайд 31. Обработка на сервере

Проследим, как обработчик превращает недоверенные входные данные в допустимую операцию. Установление личности, проверка роли и проверка конкретного объекта решают разные задачи.

<a id="З3-С23"></a>

### Слайд 32. Определение пользователя

Обработчик — часть серверной программы, которая принимает конкретную операцию и формирует её результат. На экране псевдокод, то есть описание алгоритма понятными действиями без привязки к языку. Сначала устанавливается пользователь, затем проверяются вход и роль. После разбора данных проверяют проект и мотивацию. Сохранение должно учитывать повтор, а ответ — подтверждённый результат. Каждый шаг соответствует уже известному правилу.

Псевдокод не скрывает необходимость обработки отказа. Если условие не выполнено, путь создания прекращается и формируется согласованная ошибка. Порядок отдельных независимых проверок может отличаться в реализации, но нельзя сохранить недопустимую заявку и только потом обнаружить запрет. Мы будем читать алгоритм по смыслу, не требуя от ведущего объяснять незнакомый язык или запускать этот фрагмент.

Аутентификация — установление того, кто обращается к системе. В нашем сценарии она уже выполнена механизмом входа. Обработчик получает доверенный контекст и определяет Анну как пользователя двенадцать. Если в JSON прислали номер семь, это не делает клиента Ириной. Поэтому student_id не входит в согласованное тело создания. Сервер берёт значение из установленного пользователя. Так запрос нельзя превратить в чужую заявку простой подстановкой поля.

Мы не проектируем здесь способ выдачи и проверки сеанса. Это явная зависимость учебного примера. Важно понимать её границу: готовый вход позволяет определить пользователя, но не отменяет дальнейшую проверку роли и принадлежности объекта. Человек может быть успешно установлен и всё равно не иметь права на конкретное действие. Следующие слайды разберут эти условия отдельно.

<a id="З3-С24"></a>

### Слайд 33. Проверка входных данных

Валидация состоит из разных проверок. Сначала сообщение должно разбираться как JSON, затем поля должны иметь нужные типы и смысл. Число project_id не доказывает существование открытого проекта, а строка motivation ещё не доказывает допустимую длину.

Для текста стороны должны одинаково понимать нормализацию. Мы убираем согласованные пробельные символы только с концов и считаем кодовые точки Unicode. Внутренние пробелы остаются частью мотивации. Корректный синтаксис и допустимое предметное значение — разные условия; поэтому обработчик может прочитать JSON без ошибки и всё же отказать в создании.

<a id="З3-С25"></a>

### Слайд 34. Проверка роли

Авторизация — проверка права выполнить действие. Она следует после установления пользователя и опирается на роль и объектные условия. В нашем учебном договоре создание заявки предназначено студенту. Решение выполняет преподаватель. Анна может быть успешно вошедшим пользователем, но не вправе одобрить своё обращение. Поэтому отсутствие кнопки в интерфейсе не является достаточной защитой: сервер проверяет роль при обращении.

У преподавателя также есть ограничение по собственному проекту. Значение teacher не открывает общий доступ ко всем заявлениям. Таблица помогает различать общий тип действия и конкретный объект. При отсутствии входа используем 401, при установленном пользователе без нужного права — 403. Пользовательское сообщение объясняет отказ без обещания, что повторение того же запроса изменит полномочия.

Общая роль не устанавливает право на конкретный проект; пройдём нужную цепочку ссылок.

<a id="З3-С26"></a>

### Слайд 35. Принадлежность проекта

Проверку принадлежности выполняем по цепочке конкретных ссылок, а не по общему названию роли. Сначала из заявки 104 берём project_id и получаем проект 17. Затем читаем teacher_id этого проекта — 7 — и сравниваем с id пользователя, установленного по сеансу.

Для Ирины значения совпадают. Для другого преподавателя с id 8 роль teacher может быть той же, но сравнение не выполнится. Значит, доступ к чужому проекту не возникает только из-за знания номера заявки. Связи схемы объясняют, какие записи нужны проверке; клиент не может подтвердить право, прислав удобное ему значение teacher_id.

<a id="З3-С27"></a>

### Слайд 36. Бизнес-правила

Бизнес-правила описывают ограничения предметной области, а не синтаксис сообщения. Корректный JSON может содержать закрытый проект. Допустимый номер может ссылаться на уже занятую пару. Правильное слово accepted может прийти для заявки, по которой итог уже сохранён. Поэтому обработка проверяет текущее состояние и контекст операции. Не все правила используются в каждом запросе: открытый набор нужен созданию, а исходный статус — решению.

Текущее состояние может измениться между чтением и записью. Это означает, что предварительное условие надо поддержать способом сохранения, а не только отдельным ранним запросом. Для повтора такую защиту даёт уникальная пара. Для перехода можно использовать условное обновление из pending с проверкой результата. Мы не разрабатываем большой код, но явно показываем, какое правило должно оставаться истинным.

Отдельные нарушенные условия должны давать различимые причины отказа.

<a id="З3-С28"></a>

### Слайд 37. Обработка отказов

Отказ должен сохранять согласованное состояние. Если мотивация короткая, новая заявка не возникает. Если пара занята, существующая запись не дублируется. Если проект закрыт, отказ относится к новой подаче, а не к удалению старых заявок. В таблице закреплены причины и формат результата для наших примеров. Числовые коды соответствуют общей семантике HTTP, машинные имена являются договором именно этого сервиса.

Неожиданный технический сбой рассматривается отдельно. Его нельзя выдавать за недопустимую мотивацию или отсутствие права. Подмена причины заставит пользователя исправлять то, что не связано с проблемой. Внутренние сведения помогают сопровождению, а внешний ответ должен оставаться понятным. После любого отказа интерфейс выбирает состояние по согласованной причине, сохраняет полезный ввод и не утверждает неподтверждённый успех.

<a id="З3-С29"></a>

### Слайд 38. Формирование успешного ответа

Подтверждение строится из уже сохранённых сведений. После успешной фиксации сервер возвращает номер созданной заявки, её проект, автора и начальный статус. Номер не вычисляется браузером ради красивой надписи: он связывает сообщение с существующей записью.

Здесь заканчивается серверная операция создания, но не исчезает риск передачи ответа. Если связь оборвалась после фиксации, база не должна автоматически удалять заявку. Дальнейшее чтение поможет установить её наличие. Это различие понадобится при полном проходе заявки через все части приложения.

<a id="З3-П4"></a>

### Слайд 39. Практика: Проверки сервера

Учебный случай: организатор 11 меняет событие владельца 12.

Роль организатора подтверждена. event.owner_id=12. Специального общего доступа нет.

Какой результат соответствует правилу? Сначала запишите прогноз. Затем исследуйте наблюдения в дополнении, выберите решение и поясните, почему остальные варианты не подходят.

#### Ответ и разбор для преподавателя

Обоснованный вывод: Отказ в изменении.

owner_id=12 не совпадает с исполнителем 11. Одна роль организатора не разрешает изменение чужого объекта.

<a id="З3-Т4"></a>

### Слайд 40. Самопроверка · Вопрос 4

Ирина имеет роль teacher и владеет проектом, но заявка уже accepted. Что проверить?

Выберите вариант и объясните, какое условие делает его допустимым. Сначала сформулируйте собственное обоснование, затем сравним его с разбором.

#### Ответ и разбор для преподавателя

Правильный вариант: Допустимость перехода из текущего состояния.

Роль и принадлежность дают полномочие на объект, но не разрешают переход, которого нет в модели. Итоговое состояние сохраняется.

## Вопрос 5. Работа с базой

<a id="З3-С30"></a>

### Слайд 41. Работа с базой

Проверки должны выдерживать изменения между чтением и записью. Разберём параметры SQL, ограничения и конкурирующие операции, не приписывая транзакции лишних гарантий.

<a id="З3-С31"></a>

### Слайд 42. Добавление записи

Эс-кью-эль, SQL, — язык работы с реляционными данными. SELECT выбирает указанные столбцы, FROM задаёт таблицу, WHERE ограничивает строки. В нашем коротком примере получаем сведения проекта семнадцать. Значение передают параметром, отдельно от текста команды. Это позволяет не строить команду простым склеиванием произвольного пользовательского ввода. Мы показываем назначение частей, не требуя запоминать синтаксис.

Если строка не найдена, это результат поиска в текущем состоянии, а не доказательство ошибки самого языка. Обработчик должен выбрать предусмотренное поведение. Чтение проекта нужно и для карточки, и для проверки создания. В разных операциях набор выбираемых полей может отличаться. Мы не получаем все данные только потому, что таблица технически доступна: запрос должен соответствовать задаче и праву пользователя.

INSERT добавляет строку. В перечне столбцов указано, какие значения сохраняются. Проект и мотивация взяты из проверенного содержимого, студент — из установленного сеанса. Начальное pending назначено системой. Время формируется при создании. RETURNING позволяет получить назначенный идентификатор, чтобы затем вернуть номер сто четыре в ответе. Мы не просим Анну самостоятельно выбрать этот номер.

Команда может встретить ограничение уникальности, если другая попытка уже заняла ту же пару. Это не должно превращаться во второй успешный результат или необработанную техническую надпись. Обработчик сопоставляет ожидаемый конфликт с договорённой причиной. При неожиданном сбое используются другие сведения для разбора. Такой подход сохраняет смысл правила и даёт интерфейсу конкретный результат. Код показан как короткий поясняющий пример, а не полная серверная программа.

Для чтения интерфейсу потребуются также названия из связанных таблиц.

<a id="З3-С32"></a>

### Слайд 43. Связанные данные в SQL

JOIN соединяет связанные строки. Короткие обозначения a и p помогают читать, из какой таблицы взято поле. Условие соединения сопоставляет номер проекта из заявки с ключом проекта. Условие WHERE ограничивает результат текущим студентом. Так Анна получает название темы рядом с собственным статусом без копирования названия в каждое обращение. Запрос выражает обе нужные идеи: связь данных и отбор.

Если убрать отбор по student_id, технически можно получить чужие заявки. Поэтому право доступа нельзя считать следствием одного правильного соединения. Оно должно присутствовать в обработке и выдаче. Также соединение не добавляет несуществующие записи: заявка должна уже сохраняться. Сокращённый пример выбирает только нужные здесь поля. Для даты или мотивации договор представления может включать дополнительные согласованные значения.

<a id="З3-С33"></a>

### Слайд 44. Ограничения базы

Ограничения дополняют друг друга. Первичный ключ отличает строку, внешний поддерживает существование связанного объекта, обязательность запрещает отсутствие значения. Уникальная пара выражает правило повтора, список статусов — допустимый словарь. Ни одно из этих ограничений в одиночку не заменяет весь договор заявки. Таблица специально показывает и границу каждого средства. Это помогает не приписывать базе проверку, которую мы фактически не описали.

Некоторые правила можно дополнительно выразить в самой базе, если это оправдано архитектурой. В нашем объяснении важно распределить ответственность явно: обработчик проверяет пользователя и условия, а база поддерживает структурные ограничения. Если изменить это распределение в реализации, потребуется сохранить тот же наблюдаемый результат. Мы не делаем из выбранного учебного варианта универсальное требование ко всем системам.

Проверим, что произойдёт, когда две обработки увидят одно и то же прежнее состояние.

<a id="З3-С34"></a>

### Слайд 45. Два одновременных запроса

Две вкладки обозначают две независимые попытки, каждая со своей серверной обработкой. Стрелки к базе не означают прямое подключение браузера к хранилищу. Вертикальный порядок сообщений задан для объяснения конкуренции и не является шкалой длительности.

Обе обработки успели проверить одну пару: student_id 12, project_id 17. В момент каждого предварительного чтения записи ещё нет, поэтому обе ранние проверки законно проходят. Причина гонки — изменение общего состояния после чтения, а не обязательно ошибка самого SELECT.

Сначала рассмотрим фиксацию А. Её INSERT и COMMIT сохраняют заявку 104, а UNIQUE отклоняет вторую одинаковую пару. Обработчик второй попытки переводит этот результат в APPLICATION_EXISTS. Затем выбираем вариант, где первой фиксирует Б: роли победителя меняются, но допустимый итог тот же — одна запись и понятный конфликт другой попытки. Блокировка кнопки в одной вкладке не обеспечивает такой защиты между независимыми запросами.

У базы и приложения разные обязанности: ограничение отклоняет запись, обработчик объясняет конфликт.

<a id="З3-С35"></a>

### Слайд 46. Как приложение обрабатывает конфликт UNIQUE

Разберём перевод результата базы в договор API. Ограничение UNIQUE отклонило вторую пару 12 и 17. Обработчик должен распознать именно этот конфликт, завершить неуспешную операцию и сообщить APPLICATION_EXISTS с кодом 409.

Нельзя превращать любую ошибку базы в «заявка уже есть»: потеря подключения или другая ошибка требуют отдельного разбора. И нельзя считать такой POST повторением с тем же успешным ответом: в нашем договоре первая фиксация даёт создание, повтор — конфликт. Защищённая уникальность и идемпотентное поведение интерфейса API не являются одним понятием.

Уникальность пары не решает конкуренцию с закрытием набора; разберём другой общий ресурс.

<a id="З3-С36"></a>

### Слайд 47. Транзакция

Здесь конкурируют не две подачи, а подача и закрытие проекта. UNIQUE пары не отвечает на вопрос, был ли набор открыт в нужный момент. Транзакция задаёт общую границу работы: BEGIN начинает её, COMMIT фиксирует изменения, а ROLLBACK отменяет незавершённые изменения. Но один BEGIN ещё не устраняет конфликт чтения и изменения.

В выбранной дисциплине оба обработчика блокируют одну строку projects. Если первой блокировку получила подача, SELECT FOR UPDATE читает открытый проект и удерживает строку до завершения. Допустимая заявка сохраняется, COMMIT освобождает блокировку, и только затем закрытие меняет is_open. Уже созданная заявка остаётся действительной.

Во втором сценарии закрытие первым фиксирует is_open=false. Подача получает строку позже и читает уже закрытый набор; INSERT не выполняется. Общее свойство двух случаев — согласованный порядок конкурирующих изменений одной строки. Это пример конкретного способа реализации условия, а не обещание, что любая транзакция автоматически решает любую гонку.

<a id="З3-С37"></a>

### Слайд 48. Сохранение перед подтверждением

Разделим получение номера и подтверждение фиксации. INSERT может вернуть id внутри ещё незавершённой транзакции. Этот номер удобен для дальнейшей работы обработчика, но до успешного COMMIT ещё нельзя обещать клиенту устойчивое создание.

Поэтому сначала завершают работу с данными, а затем отправляют 201. Если ошибка возникла раньше фиксации, успешного подтверждения нет. Если после неё потерян только ответ, запись уже может существовать. Во втором случае безопасный следующий шаг — уточнить состояние чтением, а не предполагать, что новый POST начнёт всё с нуля.

### Слайд 52. Полный путь: от формы к запросу

Начинаем полный путь заявки сто четыре с исходного состояния. Анна вошла, проект семнадцать открыт, её предыдущей заявки нет. В форме находится согласованная мотивация. Эти условия важны: иначе следующий ответ мог бы оказаться отказом. Мы не демонстрируем новую независимую успешную заявку после уже сохранённой. Это подробный повтор той же истории с более мелким техническим разбором. Номера и данные остаются неизменными.

Пока номер сто четыре известен нам как будущий результат подготовленного примера, но интерфейс ещё не показывает его пользователю. Он появится после сохранения. Такое разграничение точки зрения помогает ведущему не перескакивать через шаги. На экране выделены значения, которые попадут в тело запроса, а личность останется в доверенном контексте сеанса.

Браузер сформировал POST на согласованный маршрут. В теле два поля. Значение project_id равно семнадцати и связано с карточкой. Мотивация совпадает с формой. Здесь нет номера заявки, потому что сервер ещё не создал запись. Нет student_id и status, поскольку клиент их не назначает. На этом шаге интерфейс показывает ожидание. Сообщение направлено серверу, но сам факт направления ещё не доказывает успешного выполнения.

Для чтения фрагмента достаточно назвать метод, путь и два значения. Мы не разбираем по буквам весь текст мотивации повторно: он уже был прочитан на форме. Важно проследить отсутствие искажения при переходе от экрана к данным. Если тело случайно содержит другой проект, нарушится пользовательский выбор, даже если запрос синтаксически корректен. Поэтому согласованность примера проверяется не только по коду ответа.

Переданные значения ещё не определяют автора: его установит сервер по сеансу.

Но к сохранению ещё рано переходить: нужно проверить проект, содержимое и отсутствие повтора.

Этот шаг показывает разницу между отсутствием поля в запросе и отсутствием значения в итоговой записи. student_id не передаётся как пользовательский ввод, но будет присутствовать в базе и ответе. Источником служит система. Такой же подход применяется к начальному статусу и времени, хотя их происхождение другое. Важно точно объяснить, откуда появляется каждое поле, чтобы не оставлять преподавателю скрытый переход.

### Слайд 54. Путь заявки: проверка проекта

Обработчик находит проект семнадцать и читает актуальные сведения. Проект существует, набор открыт. Значение teacher_id равно семи и позднее позволит Ирине получить заявку. Здесь мы не проверяем, является ли Анна преподавателем проекта: она действует как студент и не должна владеть проектом для подачи. Условие принадлежности понадобится при решении. Так проверка определяется конкретной операцией, а не механически копируется во все запросы.

Если набор закрыт, создание прекращается с причиной PROJECT_CLOSED. Существующие заявки сохраняются. Если проекта нет, это другой отказ. В конкурентной реализации проверка открытости и запись должны быть согласованы с закрытием проекта. На слайде показан успешный учебный путь, где состояние остаётся допустимым. Мы не делаем из одного раннего чтения гарантию на любое последующее время. Следующий шаг проверит мотивацию.

Открытый проект не отменяет независимую проверку мотивации.

<a id="З3-С42"></a>

### Слайд 55. Полный путь: одинаковый подсчёт длины

На слайде показан именно выбранный способ подсчёта, а не универсальное значение слова «символ». В строке «А😀» две кодовые точки. Обычная JavaScript length возвращает три единицы UTF-16, поэтому прямое сравнение этой length с границами дало бы другое правило.

После trim разворачиваем строку в последовательность кодовых точек и получаем её длину. Затем отдельно проверяем нижнюю и верхнюю границу включительно. Составной видимый знак может включать несколько кодовых точек; мы не обещаем подсчёт пользовательских графем. Совпадение договора формы и сервера важнее случайного совпадения чисел на простом русском тексте.

Допустимые значения готовы; теперь свяжем их с операцией сохранения и подтверждением.

<a id="З3-С43"></a>

### Слайд 56. Путь заявки: сохранение

На диаграмме последовательности читаем сообщения сверху вниз. Столбцы обозначают участников, а не разные копии заявки. Сплошная стрелка запроса и ответная передача показывают, какая часть сообщает следующей необходимые сведения; расстояние по вертикали не задаёт секунды.

Браузер передаёт проект 17 и мотивацию. Сервер устанавливает Анну 12 из сеанса и проверяет условия. База создаёт pending и подтверждает фиксацию заявки 104. Только после этого отправляется 201 с номером и статусом. Поэтому номер в подтверждении относится к той же записи, которую затем можно прочитать.

Последний GET — отдельная проверка доступного Анне результата, а не продолжение незавершённого INSERT. Если ответ 201 потеряется после COMMIT, запись уже может существовать; повторное чтение помогает установить её наличие. И наоборот, красивое подтверждение без сохранённой записи не соответствует показанной причинной цепочке. Важно удержать порядок «сохранение — подтверждение», а не просто перечислить названия сообщений.

Уточним, какую связь между сообщением и записью выражают номер и Location в ответе.

<a id="З3-С44"></a>

### Слайд 57. Полный путь: связать ответ с записью

Сервер отправляет успешный ответ. Номер, проект, студент и статус совпадают с сохранённой записью. Ответ сокращён, но не противоречит полной модели. Код 201 указывает создание, а pending — этап рассмотрения. Это два разных уровня результата. Один относится к выполнению операции, другой к жизненному пути заявки. Поэтому интерфейс может одновременно показать «Заявка сохранена» и «На рассмотрении» без противоречия.

Если код успешно получен, браузер имеет основание обновить представление. Если ответ потерян, этого основания у него пока нет, хотя операция завершилась. Мы сохраняем различие и не меняем задним числом состояние базы из-за отсутствия сообщения в окне Анны. на четвёртой лекции именно этот разрыв станет подготовленным инцидентом. Сейчас продолжим основной путь, в котором ответ дошёл.

Браузер должен отобразить именно подтверждённые сведения, не дополняя их собственным решением.

### Слайд 58. Путь заявки: обновление интерфейса

Браузер прочитал ответ и переключил форму в подтверждение. Пользователь видит номер сто четыре и состояние ожидания решения. Эти значения взяты из результата системы, а не придуманы локально. Текст мотивации больше не является единственным местом сведений: есть сохранённая запись. Анна может перейти в свои заявки. Это завершает критерий подачи, но не весь процесс рассмотрения. Действие Ирины произойдёт позже.

При обновлении важно не показать неподтверждённое одобрение или новую заявку с другим номером. Подготовленный макет демонстрирует ровно то, что поддерживает ответ. Если программа использует дополнительное чтение для обновления списка, оно тоже должно учитывать текущего пользователя. Мы не требуем конкретной библиотеки управления интерфейсом. Для курса существенна причинная цепочка от подтверждённого сохранения к понятной надписи.

<a id="З3-С46"></a>

### Слайд 59. Полный путь: проверка после нового входа

Анна открывает собственный список отдельным запросом. Сервер снова устанавливает пользователя и выбирает её записи. Номер сто четыре присутствует. Это показывает, что результат не зависит только от оставшегося сообщения формы. Такую же операцию можно использовать после восстановления связи, если первый ответ не дошёл. В нашем основном пути чтение просто подтверждает сохранённые сведения. При этом оно не создаёт новую заявку.

Если позднее Ирина примет решение, тот же путь вернёт обновлённый статус. Условия доступа останутся прежними: Анна видит свои обращения. Мы не вводим специальную ручную передачу результата от преподавателя студенту. Общая запись и согласованные представления уже поддерживают этот обмен. Теперь посмотрим, как та же заявка попадает в область работы Ирины через принадлежность проекта.

Проверим тот же объект со стороны ответственного преподавателя.

Чтение Ириной завершает проверку общего результата с другой стороны. Она обращается к списку проекта 17, но сервер сначала сопоставляет teacher_id этого проекта с её id 7. После проверки возвращается та же заявка 104, которую читала Анна.

Если Ирина позже примет решение, Анна увидит итог через свой маршрут чтения. Так одна запись связывает два интерфейса без общего публичного доступа ко всем мотивациям.

## Вопрос 7. Размещение приложения

<a id="З3-С48"></a>

### Слайд 63. Размещение приложения

Согласованный код должен работать в конкретной среде. Свяжем имя узла, защищённое соединение, серверный процесс и подключение к базе в доступный пользователю путь.

<a id="З3-С49"></a>

### Слайд 64. Адрес приложения

Среда — условия, в которых запущено приложение: адреса, процессы, подключения и настройки. Локальная среда удобна разработчику для подготовки изменений. Рабочая доступна пользователям. Один и тот же исходный код может использовать разные адреса базы и режимы. Поэтому успешный запуск на одном компьютере ещё не доказывает готовность для остальных. Необходимо проверить нужную конфигурацию и фактическую доступность компонентов.

Учебные записи не следует автоматически считать рабочими. Перенос версии программы и перенос данных являются разными действиями. В нашем курсе все значения условные. Мы рассматриваем схему размещения, а не предоставляем готовый промышленный сервер «Проектного навигатора». Такая граница помогает честно отделять подготовленные материалы от эксплуатации. Следующий шаг объяснит, как браузер получает адрес нужного приложения.

Для обращения браузеру нужен адрес. В локальной среде это может быть адрес собственного компьютера с номером порта. В рабочей среде обычно используется доменное имя. Порт обозначает точку обслуживания на узле. Путь внутри адреса выбирает страницу или операцию. Эти части не следует смешивать: изменение маршрута API не означает смену всей машины, а изменение домена не обязательно меняет правила заявки.

Доступность адреса требует запущенного приложения и подходящей сетевой настройки. Если процесс остановлен, красивое доменное имя само по себе не создаёт ответ. Если открывается стартовая страница, это ещё не доказывает доступ к базе. Поэтому проверку размещения связывают с конкретным полезным сценарием. На следующих слайдах разложим имя, защиту соединения и серверный процесс, чтобы понять их разные обязанности.

<a id="З3-С50"></a>

### Слайд 65. Доменное имя

Доменное имя — понятное человеку обозначение сетевого ресурса. DNS, Domain Name System, помогает сопоставлять такие имена с адресной информацией. Это отдельная служба от логики заявок. Если сопоставление недоступно или неверно, браузер может не добраться до приложения. При этом данные в базе не обязаны исчезнуть. Разделение помогает сопровождению искать причину в правильной части пути.

В примере используем условное имя, а не существующий адрес сервиса. Оно показывает роль домена в схеме. Для рабочего размещения также учитывают управление именем и сертификатом. Мы не даём пошаговую инструкцию регистрации у конкретного поставщика, потому что задача курса — проектное понимание. Дальше посмотрим, что добавляет защищённое соединение и каких свойств оно само по себе не гарантирует.

Найденный адрес помогает установить соединение; отдельно нужна защита самого обмена.

<a id="З3-С51"></a>

### Слайд 66. HTTPS

Эйч-ти-ти-пи-эс, HTTPS, использует защищённое соединение с TLS. Оно помогает защитить передаваемые данные и проверить сервер в рамках модели сертификатов. Но замок в браузере не означает, что программа правильно проверяет роль или не создаёт дубликаты. Эти свойства относятся к другим частям проекта. Поэтому защищённую передачу включают в схему, не приписывая ей решение всех задач надёжности и доступа.

Для нашего пути мотивация и сведения пользователя передаются по защищённому соединению в рабочем размещении. Затем сервер всё равно применяет правила. Если пользователь не имеет права на чужую заявку, HTTPS не делает такое действие допустимым. Сопровождение должно также понимать ошибки сертификата как отдельную причину недоступности. Мы ограничиваемся назначением средства и не настраиваем сертификаты во время лекции.

<a id="З3-С52"></a>

### Слайд 67. Процесс сервера

Сервер в нашей логической схеме — роль программы. В размещении ей соответствует запущенный процесс, то есть выполняющийся экземпляр программы. Если файлы скопированы, но процесс не работает, запросы не обслуживаются. Поэтому выпуск включает запуск и проверку. При необходимости процесс перезапускают после обновления. Нужно заранее определить, как понять, что он действительно принимает обращения, и где смотреть сведения о сбое.

Проверка только наличия процесса недостаточна. Он может работать, но не подключаться к базе. Также стартовая страница может отдаваться отдельно от операций API. Для учебного сервиса полезно проверить получение каталога и управляемый путь заявки в подходящем наборе данных. Эти действия показывают связь компонентов. Мы не добавляем конкретный менеджер процессов или операционную систему: выбор зависит от среды и команды.

Запущенный процесс сможет работать с заявками только при доступном подключении к данным.

<a id="З3-С53"></a>

### Слайд 68. Подключение к базе

Чтобы читать проекты и сохранять заявки, сервер устанавливает подключение к базе. Ему нужны адрес, имя хранилища и подходящие полномочия. Эти сведения относятся к конфигурации среды, а не к пользовательской форме. Браузер не должен получать доступ для произвольного выполнения команд в базе. Он обращается к согласованным операциям сервера, которые применяют правила. Такое разделение сохраняет выбранную архитектуру.

Если подключение недоступно, сервер не может честно подтвердить новое сохранение. Результат должен отражать сбой обработки, а технические сведения помогут сопровождению. Нельзя заменять ошибку базы сообщением о короткой мотивации. Для диагностики также полезно различать отказ подключения и нарушение ожидаемого ограничения уникальности. Один случай означает инфраструктурную проблему, другой — конфликт с текущим состоянием данных при допустимой работе базы.

<a id="З3-С54"></a>

### Слайд 69. Конфигурация

Конфигурация задаёт параметры запуска для выбранной среды. Она позволяет использовать рабочую версию с правильной базой и адресом без редактирования пользовательской формы. В таблице показаны условные имена, а не настоящие секреты. Их значения передаются подходящим способом среды размещения. Правило длины мотивации и адрес базы имеют разный смысл: первое описывает договор проекта, второе — условия подключения.

Ошибка конфигурации может выглядеть как неработающее приложение, хотя код и данные сами по себе корректны. Поэтому перед выпуском проверяют наличие параметров и соответствие нужной среде. Особенно опасно случайно подключить рабочую версию к учебному хранилищу. Мы не запускаем настройку в эфире, а показываем подготовленный перечень сведений и последствий. Этого достаточно, чтобы ведущий объяснил границу между программой и средой её выполнения.

<a id="З3-С55"></a>

### Слайд 70. Доступность компонентов

Доступность нужно оценивать по составу системы. Загрузка страницы показывает, что браузер получил оболочку. Получение каталога подтверждает ещё часть пути. Создание в контролируемом сценарии проверяет запись, но не доказывает все права и ограничения. Поэтому нельзя объявить систему готовой по одному зелёному индикатору. Нужно связать признаки с тем, что они действительно подтверждают.

Для нашего примера критерии выпуска включат доступность компонентов и подготовленные проверки основного поведения. При отказе важно понять, где оборвался путь. Ошибка имени, соединения, процесса и базы требует разных действий. Схема размещения помогает сопоставить симптом с зависимостью, а журнал и метрики дополнят её на четвёртом занятии. Теперь перейдём к управляемому выпуску новой версии и сохранению возможности восстановления.

## Вопрос 8. Выпуск версии

<a id="З3-С56"></a>

### Слайд 73. Выпуск версии

Рассмотрим выпуск как согласованное изменение программы, конфигурации и схемы данных. Проверим, что делать при неудаче и какие сведения передать сопровождению.

<a id="З3-С57"></a>

### Слайд 74. Подготовка настроек выпуска

Версия обозначает конкретный набор изменений. Перед выпуском нужно знать, что проверено и что меняется. Затем готовят конфигурацию, оценивают структуру данных и способ восстановления. Размещение выполняют по понятному порядку, после чего подтверждают работу ключевого пути. Такой процесс снижает неопределённость: при проблеме можно установить, какая версия действует и что было сделано. Случайное копирование отдельных файлов затрудняет этот разбор.

В нашем учебном случае мы показываем порядок, а не выполняем промышленный выпуск. Ожидаемые проверки ещё не являются фактически пройденными. При работе с настоящим сервисом результат фиксируют отдельно. Полезно заранее определить, что считать неудачным выпуском и кто принимает решение о возврате. Следующие слайды раскроют настройки, изменение структуры, резервную копию и ограничения отката.

Подготовка настроек предотвращает часть ошибок ещё до переключения пользователей. Проверяем, что выбрана нужная среда, подключение ведёт к правильной базе, а рабочий адрес соответствует размещению. Защищённое соединение должно подходить этому имени. Полезно иметь способ установить действующую версию, иначе разбор сообщения пользователя начнётся с догадок. При этом внутренние секреты не должны появиться на публичной странице.

Перечень на экране — готовая памятка, а не предложение аудитории что-то настроить. Ведущий объясняет назначение каждого пункта. Нельзя считать его универсальным исчерпывающим регламентом для любого сервиса. Состав зависит от архитектуры и среды. Для «Проектного навигатора» он связывает уже введённые элементы, поэтому не добавляет внезапные внешние службы и сложные механизмы, которых нет в базовой версии.

<a id="З3-С58"></a>

### Слайд 75. Обновление структуры данных

Миграция схемы — управляемое изменение структуры базы. Например, при новом правиле может понадобиться дополнительное ограничение. Перед применением проверяют, соответствуют ли ему существующие записи. Если уже есть дубликаты, добавление уникальной пары потребует отдельного решения по данным. Нельзя просто объявить изменение безопасным потому, что команда короткая. Также новая и старая версии программы должны быть согласованы со структурой.

В нашем базовом учебном наборе схема уже соответствует правилам. Мы рассматриваем миграцию как часть будущего выпуска, не изменяя данные в эфире. Если расширение добавляет необязательное поле, это одна сложность. Если удаляет сведения, это другая и может затруднить возврат. Поэтому план изменения должен включать проверку результата и условия восстановления, а не только команду выполнения.

Совместимость схемы определяет и возможность возврата после неудачного выпуска.

<a id="З3-С59"></a>

### Слайд 76. Возврат после неудачного выпуска

Таблица разделяет возврат программы и восстановление данных. Если ошибка только в новой программе и прежняя версия понимает нынешнюю схему, может оказаться достаточным вернуть код. Если схема изменилась несовместимо, простого запуска старой программы уже недостаточно.

Восстановление копии — отдельная операция с последствиями: после момента её создания могли появиться новые заявки. Поэтому до выпуска нужен проверенный порядок, который учитывает совместимость и судьбу этих записей. Сопровождению передают конкретную версию, ответственного и способ проверить результат, а не только файл с датой в имени.

<a id="З3-Т8"></a>

### Слайд 78. Самопроверка · Вопрос 8

Достаточно ли наличия файла резервной копии?

Выберите вариант и объясните, какое условие делает его допустимым. Сначала сформулируйте собственное обоснование, затем сравним его с разбором.

#### Ответ и разбор для преподавателя

Правильный вариант: Нет, нужно проверить восстановление и совместимость.

Пригодность копии подтверждается восстановлением; выпуск также требует совместимости приложения и схемы.

### Слайд 79. Итоги занятия

Запрос не является доказательством права, INSERT — доказательством фиксации, а доступная страница — доказательством полного пути. Для каждого вывода мы нашли нужное основание: сеанс, объектные проверки, ограничения записи, успешный COMMIT и проверенный сценарий выпуска. Эти различия помогут исследовать качество и сбои на следующем занятии.

### Слайд 80. Вопросы от аудитории

Какие вопросы остались по решениям этой лекции? Можно вернуться к конкретному условию, связи схемы или результату. Подготовленные вопросы на экране помогут начать обсуждение, если требуется разобрать один из ключевых выводов.

#### Ответ и разбор для преподавателя

Почему номер студента не передаётся при создании?
Сервер устанавливает пользователя по подтверждённому сеансу. Число в теле запроса контролирует отправитель, поэтому оно не может служить доказательством личности. Анна передаёт выбранный проект и мотивацию. Обработчик добавляет доверенную принадлежность и начальный статус. Скрытое поле формы не меняет степень доверия к клиентским данным.

Что произойдёт при двух одновременных запросах?
Оба обработчика могут увидеть отсутствие заявки до вставки. Уникальность пары в базе не позволит сохранить два экземпляра. Один запрос создаст запись, а другой получит предусмотренный отказ повтора. Сервер переводит технический результат в понятное сообщение. Отключение кнопки снижает случайные повторы, но не заменяет это правило для другой вкладки.

Когда можно показать подтверждение?
После подтверждённого сохранения. Отправка запроса ещё не означает создания заявки. Если ответ потерялся, браузер сообщает неопределённость и предлагает проверить свои заявки после восстановления связи. Нельзя удалять сохранённую запись только потому, что пользователь не увидел подтверждение. Для диагностики связывают события запроса и читают фактический результат в данных.
