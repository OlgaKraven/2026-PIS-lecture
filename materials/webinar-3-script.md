## Слайд 7. Ответственность сервера (З3-С04)

Плановое время: 227 с. Блок: Части приложения.

### Текст на экране

Сеанс — сведения о ранее подтверждённом входе; сервер связывает с ними каждый запрос.

### Визуальный материал

Ответственность браузера. Последовательность подписанных блоков. 1. Подготовка: Получить выбранный проект и мотивацию. 2. Отправка: Передать согласованное обращение. 3. Представление: Показать ожидание, результат или неопределённость.

Ответственность сервера. Последовательность подписанных блоков. 1. Установить пользователя: Получить Анну из действующего сеанса. 2. Проверить: Формат, роль, проект, текст и повтор. 3. Сохранить: Создать согласованную запись. 4. Ответить: Сообщить подтверждённый результат.

Интерактивная схема: Ответственность сервера. Исходные условия и сценарии: Разбор материала: Сеанс — сведения о ранее подтверждённом входе; сервер связывает с ними каждый запрос.

### Текст выступления

Браузерная часть управляет представлением и взаимодействием. Она помогает Анне заполнить форму и передаёт обращение в согласованном формате. Затем читает результат и выбирает соответствующее состояние интерфейса. Это не означает право назначить student_id или итоговый статус. Клиентские данные могут быть изменены, а локальные сведения о проекте — устареть. Поэтому сервер не считает внешний вид страницы доказательством допустимости операции.

Такое разделение полезно и при разработке. Изменение расположения поля не должно менять правило допустимой длины. Замена интерфейса не должна открывать дополнительные права. Серверный договор позволяет нескольким представлениям обращаться к одной логике. В нашем примере реализуется только согласованный веб-путь, но принцип объясняет, почему правила не прячут исключительно в код кнопки. Дальше посмотрим на сторону, которая принимает окончательное решение.

Сервер принимает запрос и применяет правила независимо от состояния страницы. Он определяет пользователя по сеансу, проверяет структуру данных и право выполнить действие. Для создания заявки нужен студент, открытый существующий проект, допустимая мотивация и отсутствие предыдущей пары. Затем сервер организует сохранение. Только после подтверждения записи можно формировать успешный результат. Такой порядок исключает обещание действия, которое ещё не завершилось.

На схеме показаны логические шаги, а не обязательное число функций в программе. Реализация может распределить их между несколькими частями. Существенно, чтобы проверки не исчезли и чтобы ошибка ограничения данных превратилась в понятный договорённый ответ. Если два обращения пришли почти одновременно, простое предварительное чтение ещё не гарантирует отсутствие повтора. Этот случай позже разберём на временной последовательности.

### Текст выступления

Самостоятельное дополнение вне основного 120-минутного плана. Блок: Части приложения.

### Текст на экране



### Визуальный материал

Учебный случай: клиент бронирования отправляет user_id=77. Сеанс принадлежит пользователю 52. JSON можно изменить вручную. Операция выполняется от текущего пользователя.

### Текст выступления

Учебный случай: клиент бронирования отправляет user_id=77.

Сеанс принадлежит пользователю 52. JSON можно изменить вручную. Операция выполняется от текущего пользователя.

Работайте командой: аналитик выделяет правило, оператор записывает общий результат, проверяющий ищет контрпример. После каждого шага меняйтесь ролями. Шаг 1. Установите источник личности. В JSON user_id=77, а серверный сеанс принадлежит 52. Аналитик записывает доверенный ID и значение из недоверенного тела.

Шаг 2. Соберите серверную запись. Для бронирования выбран учебный сеанс 23, поле session_id. Это ID встречи, а не сеанс входа. Оператор создаёт пару (user_id, session_id), подставляя личность по сеансу.

Шаг 3. Проверьте подмену. Проверяющий повторил запрос с user_id=88 в теле при том же сеансе. Укажите владельца записи и число записей, которые запрос вправе создать от имени 88.

Сначала дайте команде получить свой результат. Проверяйте структурированные поля по шагам; причины решения обсуждайте отдельно, поскольку свободное объяснение не оценивается автоматически. Сравните итог с прогнозом.

### Ответ и разбор для преподавателя

Шаг 1. Установите источник личности. Доверенный ID: 52. Личность устанавливается аутентифицированным сеансом. ID из тела: 77. Значение тела контролирует клиент.

Шаг 2. Соберите серверную запись. user_id: 52. Не копируйте личность из JSON. session_id: 23. Объект записи берётся из условия и отдельно проверяется.

Шаг 3. Проверьте подмену. Владелец записи: 52. Смена тела не меняет аутентифицированного пользователя. Записей от имени 88: 0. Нельзя создавать записи от имени произвольного пользователя.

Итог: Проверенный сеанс устанавливает пользователя 52. Значение 77 в JSON не подтверждает личность и не даёт права действовать от её имени.
