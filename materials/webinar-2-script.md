### Текст выступления

У каждого значения на экране есть предметный владелец. Название относится к проекту, имя — к пользователю, мотивация и статус — к заявке. Если скопировать все подписи в одну случайную строку интерфейса, внешне макет получится, но источник обновления останется неясным.

Такое рассуждение связывает UI, то есть элементы взаимодействия, с UX — тем, как человек проходит путь и понимает результат. Поле на макете становится основанием проверить модель данных, а не просто местом для текста.

### Текст выступления

Учебный случай: список заказов показывает название книги и состояние заказа.

Название принадлежит книге. Состояние принадлежит заказу. В списке нужны оба значения.

Работайте командой: аналитик выделяет правило, оператор записывает общий результат, проверяющий ищет контрпример. После каждого шага меняйтесь ролями. Шаг 1. Определите источники полей. Аналитик подписывает источник: название принадлежит книге, состояние — заказу. Введите сущности для двух экранных полей.

Шаг 2. Соедините записи. Данные: books {(9, «Архив»), (10, «Сети»)}; orders {(208, book_id:10, status:new)}. Оператор соединяет orders.book_id = books.id. Укажите ID книги и её название для заказа 208.

Шаг 3. Проверьте карточку. Проверяющий видит «Архив / new» для 208. Назовите неверное поле и верный статус, который должен сохраниться при исправлении.

Сначала дайте команде получить свой результат. Проверяйте структурированные поля по шагам; причины решения обсуждайте отдельно, поскольку свободное объяснение не оценивается автоматически. Сравните итог с прогнозом.

### Ответ и разбор для преподавателя

Шаг 1. Определите источники полей. Источник названия: книга. Название описывает издание. Источник состояния: заказ. Состояние относится к конкретному заказу.

Шаг 2. Соедините записи. ID книги: 10. Соединение идёт по book_id, а не по позиции строки. Название: Сети. Книга 10 имеет название «Сети».

Шаг 3. Проверьте карточку. Неверное поле: название. Состояние заказа верно; неверно соединено название. Сохраняемый статус: new. Исправление отображения книги не меняет состояние заказа.

Итог: Поле состояния относится к заказу, название — к книге; соединение должно сохранять их предметную связь.

### Текст на экране

### Визуальный материал

Путь студента. Последовательность подписанных блоков. 1. Каталог: Анна видит доступные учебные проекты. 2. Карточка: Читает описание и состояние набора. 3. Форма: Вводит мотивацию для выбранного проекта. 4. Мои заявки: Проверяет сохранение и позднее решение.

Карта экранов. Схема. Блоки: Каталог; Карточка проекта 17; Форма проекта 17; Подтверждение; Мои заявки. Связи: Каталог — Карточка проекта 17: Выбор проекта; Карточка проекта 17 — Форма проекта 17: Подать заявку; Форма проекта 17 — Подтверждение: Успешное сохранение; Подтверждение — Мои заявки: Проверить заявку.

Интерактивная схема: Путь Анны и сохранённый контекст. Исходные условия и сценарии: Успешная подача: Анна 12; проект 17 открыт; допустимая мотивация.

### Текст выступления

Схема удерживает один выбранный проект на всём пути Анны. Каталог помогает сделать выбор, карточка — понять задачу и доступность набора, форма — передать мотивацию. Переход между экранами не должен заставлять заново выбирать объект или вводить его технический номер вручную.

Разбираем конкретный случай: Анна 12 выбирает открытый проект 17. Форме нужен этот project_id и текст; student_id не является ещё одним полем для свободного ввода. После успешного сохранения возникает заявка 104, которую можно прочитать в своём списке.

Если карточка и форма случайно относятся к разным проектам, отдельные экраны могут выглядеть убедительно, но путь уже нарушен. Если кнопка показывает успех до подтверждения, переход обещает ещё не установленный результат. Поэтому связь экранов проверяется по данным и смыслу, а не только по наличию ссылок между макетами.

Откройте «Развернуть схему». Начните с шага 0; двигайтесь по «Далее» синхронно с объяснением. После результата вернитесь к обзору и сопоставьте условие с выводом. Подсветка выделяет части модели, а не изображает выполнение алгоритма. Предусмотрено 16 с на показ подписанных элементов.

## Слайд 43. Загрузка данных (З2-С32)

Плановое время: 243 с. Блок: Состояния интерфейса.

### Текст на экране

Состояние интерфейса описывает обмен, а статус заявки — сохранённый результат рассмотрения.

### Визуальный материал

Состояния интерфейса и заявки. Таблица. Столбцы: Надпись; Объект состояния; Смысл. Строка 1: Отправляем заявку…; Интерфейс; Ожидаем ответ обработки. Строка 2: На рассмотрении; Заявка; Запись существует, решения ещё нет. Строка 3: Не удалось получить ответ; Интерфейс; Результат операции неизвестен. Строка 4: Отклонена; Заявка; Сохранено отрицательное решение.

Загрузка данных. Подготовленный макет экрана «Загрузка моих заявок», состояние «loading».  Заголовок раздела уже виден, на месте списка сообщение «Загружаем заявки…»; пустой список не утверждается.

### Текст выступления

На экране могут появляться похожие по смыслу слова ожидания. Их нужно относить к разным объектам. «Отправляем заявку» описывает текущую работу формы. «На рассмотрении» описывает уже существующую заявку. «Не удалось получить ответ» сообщает о неопределённости интерфейса. «Отклонена» является подтверждённым результатом преподавателя. Смешение этих уровней приводит к ложным сообщениям и неправильным действиям после сбоя.

Рассмотрим обрыв после сохранения. Интерфейс ещё не знает о результате, хотя в базе уже есть pending. Поэтому он не должен заменять свою неопределённость отрицательным статусом заявки. При восстановлении связи можно получить список и обнаружить существующую запись. Так один пример связывает видимое сообщение с моделью данных, а позже — с серверной обработкой и сопровождением.

При открытии своих заявок системе нужно получить актуальные сведения. Пока ответ не пришёл, интерфейс показывает загрузку. Это отличается от состояния «Заявок пока нет». В первом случае мы ещё не знаем содержимое, во втором получили пустой результат. Если сразу рисовать отсутствие заявок, Анна может решить, что сохранённое обращение исчезло. Поэтому промежуточный экран должен честно описывать известное состояние.

Загрузка также не означает ошибку и не меняет статус заявки. В реализации она может длиться мало или заметно дольше в зависимости от условий. Мы не изображаем на слайде реальное измерение скорости. Подготовленный макет фиксирует содержание обратной связи. После успешного ответа список заменит сообщение. После отказа появится отдельное объяснение с возможным дальнейшим действием.

Когда ожидание завершилось, нужно различить успешное отсутствие записей и сбой получения.

Свяжите элементы с конкретным случаем и причинным выводом; отделяйте изменение данных от порядка объяснения. Предусмотрено 8 с на показ подписанных элементов.

### Текст на экране

### Визуальный материал

Фрагмент SQL. Оба поля обязательны. Сочетание одного студента и одного проекта встречается не более одного раза.

### Текст выступления

Первичный ключ id не защищает от двух заявок с разными номерами, но одинаковыми студентом и проектом. Для нашего правила нужно отдельное составное ограничение уникальности. Составное означает, что оно проверяет комбинацию значений. Пара двенадцать и семнадцать может встретиться один раз. Пара двенадцать и другой проект допустима. База удерживает инвариант, то есть правило, которое должно оставаться истинным для сохранённых данных. На третьем занятии увидим, почему эта защита особенно важна при почти одновременных запросах из двух вкладок. Сейчас достаточно правильно прочитать сочетание в скобках.
