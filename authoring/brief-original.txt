**Оставляем четыре вебинара по 120 минут и ориентир 60 слайдов на каждый. Но каждый слайд должен сопровождаться готовым текстом выступления: преподавателю потребуется объяснять материал по сценарию, без необходимости самостоятельно развивать тему.**

Ниже — подробная основа для последующей генерации презентаций и речи. В неё включены темы всех восьми лабораторных в форме **заранее подготовленных разборов решений**. Отдельные практические занятия для понимания материала не потребуются.

Проверочные тесты, опросы, задания аудитории и ожидание ответов исключаем. Тестирование веб-приложений сохраняем как содержательную тему исходной программы.

**1. Как должен быть устроен комплект материалов**

Для каждого занятия нужны три связанных материала.

| Материал | Что содержит | Для чего нужен |
|---|---|---|
| Презентация | Определения, схемы, макеты интерфейсов, таблицы, примеры запросов и результатов | Даёт зрительную опору |
| Сценарий выступления | Полный текст речи с привязкой к каждому слайду | Позволяет провести вебинар без импровизации |
| Подсказки ведущему | Произношение терминов, порядок объяснения схемы, указания на элементы изображения | Помогает правильно представить материал |

**Текст выступления нельзя заменять указаниями «рассказать об архитектуре» или «объяснить принцип работы API».** Такие формулировки оставляют самую сложную часть преподавателю. Нужны конкретные слова, которые он может произнести.

Например:

> «На схеме показаны три части приложения. Слева находится браузер студента. В центре — сервер, который принимает запросы и проверяет правила. Справа — база данных, в которой хранятся проекты и заявки. Рассмотрим, что происходит между этими частями после нажатия кнопки “Подать заявку”».

Основной способ демонстрации — подготовленные изображения и последовательности экранов. Программирование, настройку серверов и поиск ошибок в прямом эфире в обязательный сценарий не закладываем.

**2. Единый пример для всех четырёх занятий**

Используем учебный сервис **«Проектный навигатор»**.

Студент просматривает учебные проекты и подаёт заявку на участие. Преподаватель рассматривает заявки на свои проекты и принимает решение.

Это пример, на котором можно последовательно показать требования, интерфейс, данные, серверную обработку, тестирование, сопровождение и развитие.

Чтобы последующая генерация не внесла противоречий, заранее фиксируем правила.

| Элемент | Единое решение для всего курса |
|---|---|
| Роли | Студент и преподаватель |
| Доступ студента | Каталог проектов, подача заявки, просмотр своих заявок |
| Доступ преподавателя | Просмотр заявок на собственные проекты, принятие решения |
| Основные сущности | Пользователь, проект, заявка |
| Содержание заявки | Выбранный проект и мотивационный текст |
| Ограничение текста | От 50 до 1000 символов |
| Повторная подача | Одна заявка одного студента на один проект |
| Несколько проектов | Студент может подать заявки на разные проекты |
| Статусы | «На рассмотрении», «Одобрена», «Отклонена» |
| Изменение статуса | Преподаватель переводит заявку из состояния «На рассмотрении» в одно из двух итоговых состояний |
| Повторное рассмотрение | В первой версии отсутствует |
| Закрытый проект | Новые заявки не принимает |
| Каталог | Заранее заполнен для учебного примера |
| Уведомления | Дополнительная интеграция, которую вводим на четвёртом занятии |
| Интеллектуальный поиск | Расширение прототипа, которое рассматриваем в конце курса |

Учебные данные также сохраняем:

- студент Анна Смирнова, идентификатор `12`;
- преподаватель Ирина Павлова, идентификатор `7`;
- проект «Сайт студенческого клуба», идентификатор `17`;
- заявка Анны, после её создания, имеет идентификатор `104`.

**Повторное появление этого примера допустимо, когда меняется предмет рассмотрения.** На первом занятии заявка — пользовательский сценарий, на втором — форма и объект данных, на третьем — запрос и запись в базе, на четвёртом — объект проверки и наблюдения.

Повторять одно определение заявки в четырёх лекциях не требуется.

**Обязательный подробный разбор: как получить требование из жалобы**

Исходная фраза:

> «Нужно, чтобы заявки больше не терялись».

Преподаватель последовательно показывает:

1. В чём наблюдаемая проблема: заявку отправили, но её нет в общем списке.
2. Какого результата ожидает студент: убедиться, что система приняла обращение.
3. Какого результата ожидает преподаватель: увидеть новое обращение.
4. Какое действие должна выполнить система: сохранить заявку.
5. Что должен увидеть студент: подтверждение и статус.
6. Как сформулировать требование.
7. По какому признаку можно принять результат.

На экране появляется заполненная строка:

| Обозначение | Требование | Признак выполнения |
|---|---|---|
| ФТ-01 | После успешной подачи система сохраняет заявку и показывает её студенту в разделе «Мои заявки» | В списке появляется заявка на выбранный проект со статусом «На рассмотрении» |

Здесь преподаватель объясняет, что требование должно описывать наблюдаемое поведение системы.

**Второй разбор: границы первой версии**

Показываем список пожеланий:

- каталог проектов;
- подача заявки;
- просмотр статуса;
- решение преподавателя;
- чат;
- вложения;
- видеовстречи;
- автоматический подбор проектов.

Затем объясняем, какие функции необходимы для основного сценария, а какие увеличивают объём проекта. Вложения и интеллектуальный поиск не должны незаметно появиться в базовой модели на следующих занятиях.

**Подсказки ведущему**

В сценарии должны быть явно раскрыты различия:

- проблема пользователя и требование к системе;
- пользователь и заинтересованная сторона;
- функция и требование к качеству;
- схема процесса и схема устройства приложения;
- первая версия и дальнейшее развитие.

Термины вводим перед первым использованием. Если появляется сокращение, рядом даём расшифровку и простое объяснение.

**Переход к следующему занятию**

> «Мы определили, какие действия должна поддерживать система. Теперь необходимо показать, как пользователь выполнит эти действия на экране и какие данные приложение должно для этого хранить».

**Обязательный разбор: форма заявки**

Сначала показываем содержание формы:

```text
Заявка на проект «Сайт студенческого клуба»

Почему вы хотите участвовать?
[Поле мотивационного текста]

От 50 до 1000 символов

[Подать заявку]
```

Затем последовательно рассматриваем:

1. Почему название проекта уже указано.
2. Почему студент не вводит собственный идентификатор.
3. Зачем нужна подпись поля.
4. Почему ограничение длины видно до отправки.
5. Что происходит после нажатия кнопки.
6. Как выглядит подтверждение.
7. Как сохранить введённый текст при ошибке.

Пример сообщения:

> «Добавьте описание: минимум 50 символов. Сейчас введено 32».

Сообщение должно объяснять, какое действие исправит ситуацию. Подписи полей, инструкции и понятная обратная связь соответствуют рекомендациям [W3C по доступным формам](https://www.w3.org/WAI/tutorials/forms/).

**Отдельный важный фрагмент: состояния интерфейса и состояния заявки**

Здесь легко получить смысловую путаницу, поэтому нужен самостоятельный слайд.

| Состояние | Что означает |
|---|---|
| «Отправляем заявку…» | Интерфейс ожидает результат запроса |
| «На рассмотрении» | Заявка уже существует и ожидает решения |
| «Не удалось получить ответ» | Интерфейс не знает, завершилась ли операция |
| «Отклонена» | Преподаватель принял отрицательное решение |

Обрыв связи сам по себе не доказывает, что заявка не сохранилась. Этот момент далее понадобится при разборе API и повторной отправки.

**Обязательный разбор: от формы к данным**

На экране появляется таблица:

| Что видит пользователь | Откуда берётся значение |
|---|---|
| Название проекта | Из данных проекта |
| Имя студента | Из данных текущего пользователя |
| Мотивационный текст | Из заполненной формы |
| Статус | Устанавливается системой |
| Дата подачи | Формируется при создании заявки |

После этого вводим структуру:

| Сущность | Основные поля |
|---|---|
| Пользователь | `id`, `full_name`, `email`, `role` |
| Проект | `id`, `title`, `description`, `teacher_id`, `is_open` |
| Заявка | `id`, `project_id`, `student_id`, `motivation`, `status`, `created_at` |

Для состояний используем неизменное соответствие:

| В данных | На экране |
|---|---|
| `pending` | На рассмотрении |
| `accepted` | Одобрена |
| `rejected` | Отклонена |

**Подсказки ведущему**

Схему данных объясняем в фиксированном порядке:

1. Что означает каждый прямоугольник.
2. Что означает одна строка внутри него.
3. Как определяется конкретная запись.
4. Что связывает записи.
5. Какие ошибки предотвращают ограничения.

Необходимо проговорить, что связь по идентификатору позволяет хранить заявку без повторного копирования всего описания проекта.

**Переход к следующему занятию**

> «Теперь у нас есть экраны и структура данных. На следующем занятии разберём, как действие в браузере превращается в запрос, как сервер его обрабатывает и как возникает запись в базе».

| Изменить статус заявки | `PATCH /api/applications/104` |

**Обязательный разбор: создание заявки**

Показываем упрощённый запрос. Механизм входа считаем уже работающим.

```http
POST /api/applications
Content-Type: application/json

{
  "project_id": 17,
  "motivation": "Хочу разработать каталог мероприятий и личный кабинет участника студенческого клуба."
}
```

Объясняем:

- `project_id` указывает выбранный проект;
- `motivation` содержит текст формы;
- студента сервер определяет по действующему сеансу;
- начальный статус назначает сервер.

После сохранения показываем ответ:

```http
201 Created
Location: /api/applications/104
Content-Type: application/json

{
  "id": 104,
  "project_id": 17,
  "student_id": 12,
  "status": "pending"
}
```

На слайде явно указываем, что это **сокращённый пример ответа**. Код `201 Created` означает создание ресурса. [Справочник MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/201).

Следующим слайдом показываем не новый успешный запрос, а попытку повторной подачи:

```http
409 Conflict
Content-Type: application/json

{
  "code": "APPLICATION_EXISTS",
  "message": "Вы уже подали заявку на этот проект."
}
```

Выбор `409` для этого случая фиксируем в договоре нашего API как конфликт с текущим состоянием системы. [Описание статуса в MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/409).

Для мотивационного текста недопустимой длины используем `422`: сервер понимает формат запроса, но не может принять его содержимое. [Описание статуса в MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/422).

**Обязательный разбор: почему проверки кнопки недостаточно**

Последовательность изображений:

1. Кнопка становится недоступной после нажатия.
2. Пользователь открывает вторую вкладку.
3. Два запроса поступают почти одновременно.
4. Сервер проверяет правила.
5. Ограничение базы не позволяет сохранить две одинаковые пары `student_id` и `project_id`.

Составное ограничение уникальности действительно позволяет запретить повтор одной комбинации значений. При этом оба поля в нашей модели обязательны. [Документация PostgreSQL](https://www.postgresql.org/docs/current/ddl-constraints.html).

Это развитие материала второго занятия: ранее объясняли правило, теперь показываем, как система поддерживает его при одновременных действиях.

**Подсказки ведущему**

Для примеров кода нужен один подход:

- HTTP и JSON показываем как реальные форматы;
- SQL используем только в коротких поясняющих примерах;
- серверную логику показываем в явно обозначенном псевдокоде;
- каждый фрагмент сопровождаем объяснением на обычном языке.

Нельзя внезапно переходить между несколькими языками программирования или требовать от ведущего самостоятельного чтения большого фрагмента кода.

**Переход к следующему занятию**

> «Мы разобрали, как система выполняет запрос. Теперь необходимо определить, как обнаружить неправильное поведение, найти причину сбоя и понять, какие изменения принесут пользу».

**Основная линия:** показать, как проверяют систему, наблюдают за её работой и обоснованно расширяют возможности.

**Результат занятия:** готовые примеры проверок, разбора сбоя, аналитики и проектирования дополнительной функции.

| Слайды | Время | Содержание блока | Что показываем |

**Обязательный разбор: проверки приложения**

Показываем заполненные примеры. Это материал преподавателя, аудитория ничего не выполняет.

| Ситуация | Ожидаемый результат |
|---|---|
| Студент подаёт корректную заявку на открытый проект | Создаётся одна заявка со статусом `pending` |
| Введено 49 символов | Заявка не создаётся, интерфейс показывает ошибку |
| Введено ровно 50 символов | Ограничение минимальной длины выполнено |
| Введено 1001 символ | Заявка не создаётся |
| Студент повторно подаёт заявку на тот же проект | Новая запись не появляется |
| Студент пытается принять собственную заявку | Сервер отказывает в операции |
| Другой преподаватель пытается изменить заявку | Сервер отказывает в операции |
| Проект закрыт | Новая заявка не создаётся |

У каждого примера должны быть исходные условия. Например, успешное создание проверяют для студента, у которого ещё нет заявки на выбранный проект.

**Разбор сбоя: пользователь не получил подтверждение**

Сюжет:

1. Анна нажала «Подать заявку».
2. Сервер сохранил заявку.
3. Ответ не дошёл до браузера из-за обрыва связи.
4. Интерфейс сообщает, что результат пока не удалось подтвердить.
5. После восстановления связи приложение получает список заявок.
6. Анна видит уже созданную заявку № 104.

Этот пример связывает интерфейс, серверную обработку и сопровождение. Он позволяет объяснить, почему сообщение «Ошибка связи» нельзя автоматически заменять утверждением «Заявка не сохранена».

Логи, метрики и сведения о прохождении запроса помогают исследовать такие ситуации с разных сторон. Эти виды данных описаны в [материалах OpenTelemetry о наблюдаемости](https://opentelemetry.io/docs/concepts/observability-primer/).

**Разбор аналитики**

Используем явно обозначенные **условные учебные данные**.

За один выбранный период среди одной группы пользователей:

| Этап | Число уникальных пользователей |
|---|---:|
| Открыли каталог | 100 |
| Открыли карточку выбранного проекта | 60 |
| Открыли форму заявки | 40 |
| Успешно подали заявку | 25 |

Здесь необходимо объяснить:

- что именно считаем;
- за какой период;
- почему считаем пользователей, а не все нажатия;
- что означает успешная подача;
- как выбираем знаменатель при расчёте доли.

Например, доля подавших заявку среди открывших форму составляет `25 / 40 = 62,5 %`.

По одной воронке нельзя установить причину потерь. Она показывает участок, который следует исследовать. Преподавателю нужен готовый текст с этим ограничением.

**Разбор интеграции: уведомление преподавателю**

Порядок фиксируем:

1. Система принимает и сохраняет заявку.
2. После успешного сохранения обращается к сервису уведомлений.
3. При успешной доставке фиксирует результат.
4. При сбое отдельно регистрирует проблему доставки.
5. Сама заявка продолжает существовать.

В учебном варианте повторную отправку рассматриваем как отдельное действие сопровождения. Если в последующей генерации появится автоматическая очередь повторов, её нужно явно добавить в архитектуру и объяснить.

**Разбор инновационного прототипа**

Расширение: поиск проектов по описанию интересов.

Пример запроса:

> «Хочу заниматься интерфейсами и делать сервисы для студенческих организаций».

На экране показываем:

- поле запроса;
- найденные существующие проекты;
- краткое объяснение соответствия;
- переход в обычную карточку проекта.

Затем показываем ошибочный результат и объясняем ограничения. Поиск помогает выбрать проект, а заявку студент подаёт через уже рассмотренный механизм.

Важно отдельно обозначить, какие элементы относятся к базовой версии, а какие появляются только в расширении.

**8. Требования к отображению материала**

Большая презентация должна менять способ объяснения по ходу занятия.

| Тип материала | Как использовать |
|---|---|
| Определение | Короткая формулировка, один пример и пояснение границ понятия |
| Схема процесса | Последовательность действий с указанием исполнителя |
| Схема устройства | Части приложения и ответственность каждой части |
| Макет экрана | Конкретная задача пользователя и выделенный элемент |
| Последовательность экранов | Изменение состояния после действия |
| Сравнение вариантов | Одна конкретная разница и её последствие |
| Таблица данных | Небольшое число записей, достаточное для объяснения |
| Код или запрос | Короткий фрагмент с выделением рассматриваемой строки |
| График | Подписанные оси, единицы, период и объяснение показателя |
| Разбор ошибки | Исходные условия, наблюдаемое поведение, причина, решение |

Для изображения недостаточно задания «добавить красивую схему». В описании должны быть перечислены элементы, связи и подписи.

Например:

> «Показать три блока: браузер, сервер, база данных. Пронумеровать действия: отправка запроса, проверка, сохранение, возврат результата. На этом слайде выделить только проверку на сервере».

Для пошаговой последовательности соседние слайды могут использовать одну основу, но каждый должен добавлять новое состояние или объяснять следующий шаг.

Декоративные фотографии компьютеров и абстрактных сетей не должны заменять содержательные изображения.

**9. Паспорт каждого слайда**

При генерации текста следует использовать единый формат:

```text
Идентификатор: З3-С18
Название слайда:
Плановое время:

Смысл слайда:
Какую одну мысль необходимо объяснить.

Текст на экране:
Короткие формулировки для презентации.

Визуальный материал:
Что конкретно изображено.
Какие элементы подписаны.
Что выделено.

Текст выступления:
Полная речь преподавателя.

Указания ведущему:
Куда обратить внимание.
В каком порядке объяснять элементы.
Как произнести новый термин.

Переход:
Готовая фраза к следующему слайду.

Связи:
Какие ранее введённые понятия используются.
Какое требование или правило проекта раскрывается.

Источник:
Для технических утверждений, если требуется.
```

Внутренние поля «Связи» и «Источник» помогают проверке. Их не требуется зачитывать.

**Пример фрагмента речи для слайда о повторной заявке**

> «Рассмотрим ситуацию, когда студент повторно нажимает кнопку подачи заявки. Причины могут быть разными: первый ответ пришёл с задержкой, пользователь обновил страницу или открыл приложение во второй вкладке.
>
> По правилам нашего сервиса у одного студента может быть только одна заявка на конкретный проект. Поэтому повторное обращение не должно создавать ещё одну запись.
>
> На схеме выделена пара значений: номер студента и номер проекта. В нашем примере это студент 12 и проект 17. Наличие заявки с такой парой означает, что повторную заявку создавать нельзя.
>
> В интерфейсе мы можем временно отключить кнопку после нажатия. Это уменьшает число случайных повторов. Однако запрос может поступить и из другой вкладки, поэтому правило проверяет сервер, а база данных поддерживает ограничение уникальности.
>
> Пользователь при этом должен получить понятное сообщение: “Вы уже подали заявку на этот проект”. После сообщения можно предложить перейти в раздел “Мои заявки”.
>
> Обратите внимание: система предотвращает повторную заявку на тот же проект. Подать заявку на другой проект студент по нашим правилам может».

Такой текст объясняет изображение, причину решения и его границы.

**10. Как обеспечить продолжительность**

Две минуты — среднее время на слайд. Распределение будет разным:

- титульный слайд занимает меньше минуты;
- определение с примером — около полутора–двух минут;
- сложная схема — несколько минут;
- пошаговый разбор распределяется на последовательность слайдов.

Приведённый план содержит **по 120 минут и 60 слайдов в каждом занятии**. Время включает объяснение визуальных материалов и переходы, без опросов и самостоятельной работы.

Однако соответствие текста времени проверяется отдельно. Основная формула:

**Время выступления = объём произносимого текста / темп чтения + предусмотренные паузы.**

Для начального расчёта можно принять около 110 слов в минуту. Это рабочее допущение, которое нужно заменить темпом конкретного преподавателя после пробного чтения.

При таком допущении двухминутный слайд потребует примерно 200–220 произносимых слов, в зависимости от пауз. Поэтому заметка из двух предложений не сможет обеспечить запланированное время.

Если готовый материал оказывается коротким, добавляем содержательный разбор: пример, причину решения, пограничную ситуацию. Повторять тезисы другими словами для увеличения времени не следует.

**11. Правила проверки согласованности после генерации**

Проверку нужно проводить и внутри каждого занятия, и между всеми четырьмя.

| Что проверяем | Какую проблему ищем |
|---|---|
| Покрытие программы | Исчезнувшая тема или тема, упомянутая только названием |
| Последовательность | Использование понятия до его объяснения |
| Терминология | Несколько названий одного объекта без пояснения |
| Роли | Неожиданное появление администратора или дополнительных полномочий |
| Правила | Изменение ограничений между занятиями |
| Статусы | Разные наборы состояний и несовместимые переходы |
| Данные | Поля на экране, которых нет в модели, или неверные идентификаторы |
| API | Изменение маршрутов, названий полей и форматов результатов |
| Серверная логика | Доверие к переданному клиентом номеру студента или статусу |
| Иллюстрации | Несоответствие схемы речи преподавателя |
| Примеры | Нарушение собственных ограничений, например слишком короткая «корректная» мотивация |
| Повторы | Несколько слайдов с одинаковой мыслью и примером |
| Продолжительность | Недостаточный объём речи или перегруженные блоки |

| Готовность ведущего | Места, в которых ему необходимо самому придумать объяснение |
